# Accounting Function Strategy / Operating Model / Organization Design

**Topic:** TOPIC-01-001  
**Capabilities:** CAO-01-001, CAO-01-002, CAO-01-003  
**Knowledge type:** PRINCIPLES + PRACTICE. This is an operating-model topic; it does not manufacture IFRS/US GAAP/UK GAAP/AASB recognition rules.

## CAO objective
Design an accounting function that produces timely, controlled and explainable books and reporting while scaling with transaction volume, entity complexity, reporting obligations and change.

## Decision model
1. **Context gate.** Capture entities, frameworks, reporting deadlines, audit/public-company obligations, transaction volumes, systems, geographies, languages, time zones and expected 12–24 month change.
2. **Work taxonomy.** Map record-to-report, subledgers, technical accounting, consolidation, statutory reporting, controls, audit support, master data and accounting systems ownership. Separate accounting ownership from FP&A, tax operations, treasury operations, procurement and HR operations.
3. **Risk-tier the work.** Score judgment, materiality, regulatory exposure, data complexity, frequency and reversibility. High-judgment/high-risk work stays close to accountable accounting leadership; repeatable work is a candidate for standardization, shared service or automation.
4. **Choose service model.** For each activity decide local, regional, global COE/shared service, outsourced, or system-automated ownership. Do not centralize solely for labor arbitrage; consider control evidence, local statutory knowledge, handoffs and resilience.
5. **Set accountability.** Every material accounting process has one accountable owner, named preparers/reviewers, escalation path, evidence standard, service expectation and backup.
6. **Design organization.** Translate the activity model into leadership spans, technical specialists, process owners, systems/data ownership and regional/local roles. Avoid organizing only around current people.
7. **Capacity gate.** Model baseline workload plus close peaks, audit/statutory peaks, projects, leave and growth. Identify single points of failure.
8. **Control gate.** Confirm segregation of duties, privileged access, journal/reconciliation review, change governance and evidence retention remain viable under the proposed model.
9. **Transition plan.** Sequence people, process, data and system changes; define parallel runs and exit criteria. Do not migrate unstable processes without documenting the failure modes.
10. **Measure.** Track close timeliness, reconciliation quality, late adjustments, audit findings, aged exceptions, automation failure rate, capacity hotspots and recurring manual work.

## Operating-model artifact
The CAO should produce:
- current-state activity/ownership map;
- target-state service-delivery matrix;
- organization and accountability design;
- control/SoD impact assessment;
- capacity model with peak assumptions;
- transition waves, dependencies and exit criteria;
- KPI baseline and target measures;
- explicit risks, decisions and unresolved assumptions.

## Challenge tests
- If transaction volume doubles, which processes fail first?
- If a key controller is absent for two weeks during close, what stops?
- Does centralization create a local statutory/reporting knowledge gap?
- Are system administrators able to create and approve accounting outcomes?
- Is a proposed automation removing work or merely moving exception handling downstream?
- Does each material balance/process have one accountable owner?
- Can an auditor trace responsibility and evidence through the proposed model?
- Is specialist technical-accounting capacity proportional to transaction complexity rather than headcount?

## Controls and auditability
Retain approved responsibility matrices, process inventory, materiality/risk rationale, SoD assessment, outsourcing/shared-service controls, transition approvals, KPI definitions and evidence of periodic operating-model review. Changes to material accounting ownership require controlled handover and explicit acceptance.

## Systems and data
System ownership must distinguish configuration, access administration, accounting policy decisions, master-data approval and transaction processing. Integration monitoring and data lineage remain accounting-relevant even when engineering owns technical operation.

## Failure modes
- copying another company's org chart without context;
- centralizing before standardizing;
- using close speed as the only success metric;
- treating headcount reduction as automation success;
- leaving technical accounting or statutory responsibilities implicit;
- confusing process owner with every task performer;
- designing for today's volume while a major system/entity/product change is already committed.

## Framework routing
Accounting standards become relevant inside individual processes and judgments, not to the organizational design itself. When the operating model changes execution of a standards-heavy process, route the case to that topic's current framework/effective-period knowledge before changing accounting conclusions.
