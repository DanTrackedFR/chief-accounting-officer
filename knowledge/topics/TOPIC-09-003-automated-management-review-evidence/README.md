# TOPIC-09-003 — Automated Control Design / Management Review Control Design / Control Evidence Standards

## Objective
Enable the CAO to design automated and management-review controls that actually address accounting risks and to define evidence standards sufficient for an independent reviewer to understand what ran, on what population, with what result and how exceptions were resolved.

## Automated controls
Document trigger, logic/configuration, source population, interfaces, parameters, roles able to change configuration, failure behavior, exception output, monitoring and relevant IT dependencies. A control is not “automated” merely because a report is generated by a system. Establish whether the accounting decision itself is enforced/calculated by configured logic and whether that logic can change.

Automated-control design workflow: map risk -> specify rule -> validate source completeness -> define configuration/threshold -> identify change/access dependencies -> define exception handling -> test positive/negative cases -> monitor failed jobs/interfaces -> retain execution/configuration evidence -> reassess after system change.

## Management review controls
A management review must have a sufficiently precise expectation and investigation protocol. Capture the reviewer's source information, completeness/accuracy check, expected outcome/range, threshold, anomalies identified, investigation performed, evidence obtained, conclusion and follow-up. Seniority of reviewer does not compensate for vague precision.

## Evidence standard
Evidence should allow a competent independent person to answer: **who** performed/reviewed; **what** population/data was used; **when**; **what procedure/logic** was applied; **what threshold/expectation**; **what exceptions** arose; **how** they were resolved; and **what conclusion** was reached. Retain source/version identifiers where data can change after the control date.

Screenshots alone are weak when they omit population, parameters, timestamp, configuration or exception resolution. System logs alone are weak when they prove a job ran but not that the control logic/population was correct.

## CAO workflow
1. Identify mapped reporting risk and required precision.
2. Choose automated/system-enforced versus management-review response based on deterministic rule versus judgment.
3. For automated control, document logic, configuration, dependencies, change/access and exception path.
4. For review control, document expectation, disaggregation, thresholds and investigation protocol.
5. Define IPE/data completeness and accuracy controls.
6. Define minimum evidence and retention at design time.
7. Create test cases including failure/exception paths.
8. Confirm owner/reviewer and segregation.
9. Monitor changes to system, report, model, threshold and underlying accounting requirement.
10. Periodically challenge whether evidence proves performance rather than merely existence.

## Practice classification
**Required:** evidence supports actual performance and conclusion; automated controls have governed logic; review controls are precise.  
**Recommended:** standardized evidence pack and test attributes, system change linkage, exception aging.  
**World-class:** immutable execution/configuration lineage, automated population controls, exception-driven review and continuous change-impact monitoring.  
**Shortcut/risk:** screenshots without context; “reviewed, no issues”; relying on report name as proof of completeness; no monitoring of configuration changes; approvals by users who can also change the control logic.

## Framework / jurisdiction boundary
Principles are framework-independent. Accounting standards define what the control must achieve; formal ICFR evidence/testing obligations are jurisdiction/entity-status overlays. Do not claim SOX documentation is mandatory for every IFRS/AASB/FRS 102 entity.

## Scenario QA
1. ERP blocks invoices above tolerance but admin can change tolerance -> include access/change dependency.
2. Automated revenue job ran successfully but input interface dropped a file -> execution log alone fails completeness.
3. CFO reviews consolidated margin only -> challenge precision if product-level errors can offset.
4. Controller annotates variance report with investigations and source support -> stronger MRC evidence.
5. Screenshot has no date/filter/population -> insufficient evidence.
6. Control report logic changed in release -> trigger revalidation.
7. AI flags journal anomalies -> treat model/output as control input; govern version, population and human disposition.
8. Zero exceptions -> retain proof of complete population and rule execution.
9. Reviewer can post and approve same journal population -> segregation issue.
10. Audit asks how exception was resolved -> evidence must show disposition and resulting accounting/process action.
